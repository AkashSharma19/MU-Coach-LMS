# Competition group scoring and participant workspace

The change adds a group-level workspace with scoring-criterion CRUD, roster management, participant reporting, progress views, and award shortcuts. The implementation compiles, and no blocker was found in opening/back navigation or participant award preselection. The remaining blockers are non-durable criteria, synthetic progress, invalid participant availability, mismatched CSV export, prototype copy, and inaccessible workspace overlays. **Watch for:** **confirmed** criteria reset after Back; **confirmed** fabricated participant results; **confirmed** duplicate/ineligible assignments; **confirmed** unfiltered export; **confirmed** prototype-facing copy; **confirmed** modal focus escape.

**Verdict**: NEEDS_CHANGES

## High-level view

Scoring criteria initialize inside the workspace rather than the competition store and disappear whenever Back unmounts it. Every group and competition consequently starts from the same predefined criteria (**confirmed**).

Participant score, rank, progress, status, cohort, and criterion breakdown are generated from each participant’s name rather than evaluation records. The UI presents fabricated progress as competition state (**confirmed**).

The available-student drawer uses one hard-coded catalog and excludes only members of the open group. It can offer students outside the competition’s cohorts and students already assigned to another group (**confirmed**).

Search, status filtering, and rank/score sorting drive the visible table, but export reads the unfiltered participant collection. The downloaded report can disagree with the selected list view (**confirmed**).

The workspace defines a second overlay instead of using the parent’s shared modal. It neither traps focus nor restores focus to the opener, affecting every criterion, roster, and progress dialog (**confirmed**).

<details><summary>Details</summary>

## Criteria CRUD is discarded on workspace navigation

`criteria` is initialized from `INITIAL_CRITERIA` within `CompetitionGroupWorkspace` and is never passed to `CompetitionManagementPage` or written into `competitionData` (**confirmed**). Back removes the workspace from the tree, so additions, edits, and deletions reset on the next open; the same initial criteria also appear for every group and competition. The numeric guard prevents an active total above 100%, but it cannot make the configuration durable. Store criteria under the selected competition/group and pass updates through the parent.

The delete confirmation says “Existing prototype results,” exposing prototype language instead of competition-specific copy (**confirmed**). Replace it with competition/evaluation terminology.

## Participant progress is synthetic rather than evaluation-backed

The participant model derives score, progress, status, cohort, and email from a name hash, while criterion completion starts from hard-coded `assessedCount` values (**confirmed**). The progress dialog computes each criterion score from another hash and claims that evaluator submissions update scores, although no evaluation records enter the component. Connect the list, readiness summary, breakdown, filtering, sorting, and export to persisted evaluations.

## Available participants permit invalid cross-group assignment

The available list is the global `AVAILABLE_STUDENTS` constant minus only `group.members` (**confirmed**). It is not filtered by the selected competition’s cohorts, and the workspace receives no sibling memberships, so the same student can be added to multiple groups. Move the eligible roster to competition-scoped data and exclude participants assigned to any sibling group.

## CSV export does not match the selected participant view

`visibleParticipants` applies the active search, status filter, and sort, but `exportCsv` maps `participants` directly (**confirmed**). Export `visibleParticipants`, or label and offer an explicit all-participants export separately.

## Workspace dialogs bypass the shared accessible modal

`CompetitionManagementPage` has a `Modal` that traps Tab focus and restores the opener. `CompetitionGroupWorkspace` instead declares `Overlay`, which only moves initial focus; keyboard focus can leave an `aria-modal` dialog and is not returned after close (**confirmed**). Make the shared modal/drawer primitive importable and use it for criterion CRUD, participant management, and participant progress.
